# Target Portfolio To Execution Plan Design

Date: 2026-08-09

## 1. Purpose

Build a deterministic portfolio transition planner for the mock Growth /
Inflation quadrant strategy.

The planner converts a target portfolio produced by
`portfolio_decision_agent` into a strict `execution_plan` that can be passed
to `execution_agent`.

This replaces the current fragile behavior where `portfolio_decision_agent`
uses the LLM to manually calculate sell quantities, buy quantities, cash
usage, and order sequencing.

The intended boundary is:

```text
LLM decides target portfolio.
Deterministic tool calculates executable orders.
Execution agent submits and confirms the orders.
```

## 2. Problem

The current mock quadrant workflow can run, but the portfolio decision stage
can generate incomplete transition plans.

Observed example:

```text
Current portfolio:
  SPY  roughly 50%
  GLD  roughly 25%
  VGIT roughly 25%

Target portfolio:
  SPY 25%
  GLD 50%
  TIP 25%
```

The correct plan should include all four transition actions:

```text
1. Sell all VGIT because its target weight is now 0%.
2. Sell part of SPY because it moved from 50% target exposure to 25%.
3. Buy more GLD because it moved from 25% target exposure to 50%.
4. Buy TIP because it moved from 0% target exposure to 25%.
```

The LLM-produced plan only sold VGIT and bought TIP. It missed the partial
SPY reduction and GLD increase.

This is not an execution-agent problem. The execution agent correctly
executed the plan it received. The missing logic belongs in deterministic
portfolio transition code, not in prompt wording.

## 3. Design Decisions

The following decisions are fixed for this feature.

1. Use the ADK tool-call path.

   `portfolio_decision_agent` must call a local tool named
   `target_portfolio_to_execution_plan`.

2. Keep the final portfolio-decision summary shape compatible with the
   existing parser.

   The final summary should still contain:

   ```json
   {
     "decision": {},
     "target_portfolio": [],
     "execution_plan": {}
   }
   ```

3. The `execution_plan` must be generated by the tool, not manually written
   by the LLM.

4. The tool must generate an `execution_plan` that already matches the strict
   existing execution schema. The LLM must not repair, rewrite, or simplify it.

5. First-version execution rules are deliberately simple:

   - Long-only.
   - No shorting.
   - No leverage.
   - No negative cash.
   - Whole shares only.
   - Market orders only.
   - Day time-in-force only.
   - Sell orders before buy orders.
   - No tax optimization.
   - No broker-specific optimization.

6. The main success criterion is correct transition planning, not investment
   performance.

7. Prompt changes should shrink the LLM's execution responsibility instead of
   adding more instructions for manual order calculation.

## 4. In Scope

This feature includes:

- A deterministic `target_portfolio_to_execution_plan` tool.
- Prompt changes for `portfolio_decision_agent`.
- Workflow changes so `portfolio_decision_agent` calls the tool.
- Validation that the final summary's `execution_plan` matches the tool
  result.
- Tests for new-position, full-exit, partial-reduction, partial-increase,
  and basket-internal-switch scenarios.
- Trace/UI compatibility through the normal ADK tool-call record.

## 5. Out Of Scope

This feature does not implement:

- Real macro regime classification.
- Real basket-universe finalization.
- Limit orders.
- Stop loss or take profit orders.
- Fractional shares.
- Tax-aware rebalancing.
- Slippage modeling.
- Optimal trade slicing.
- Currency conversion.
- Margin or short selling.
- Portfolio optimization beyond target weights.
- A new execution agent.
- A new order confirmation workflow.

## 6. Architecture

The desired workflow is:

```text
macro_allocation_agent
  -> outputs basket weights

four basket agents
  -> each active basket outputs selected_symbol and target_weight

portfolio_decision_agent
  -> summarizes the basket reports
  -> creates target_portfolio
  -> calls target_portfolio_to_execution_plan
  -> returns decision + target_portfolio + tool-generated execution_plan

target_portfolio_to_execution_plan
  -> reads current account state
  -> reads current prices
  -> compares current portfolio with target portfolio
  -> generates current_vs_target diagnostics
  -> generates strict execution_plan

execution_agent
  -> receives only date + execution_plan
  -> submits orders in sequence
  -> confirms each submitted order
```

The planner is a deterministic calculation layer. It is not another research
agent.

## 7. Tool Name

The tool name is:

```text
target_portfolio_to_execution_plan
```

This name is intentionally direct. The tool is not only a rebalance generator.
It covers every transition from current portfolio to target portfolio:

- Initial deployment from cash.
- Basket-weight changes.
- Basket-internal symbol changes.
- Selling target-zero assets.
- Reducing overweight assets.
- Increasing underweight assets.
- Buying newly selected assets.

## 8. Tool Input

The LLM-facing input should be minimal.

Recommended input:

```json
{
  "date": "2024-09-06",
  "target_portfolio": [
    {
      "basket_id": "equity",
      "symbol": "SPY",
      "target_weight": 0.25
    },
    {
      "basket_id": "commodity",
      "symbol": "GLD",
      "target_weight": 0.50
    },
    {
      "basket_id": "tips",
      "symbol": "TIP",
      "target_weight": 0.25
    }
  ]
}
```

The LLM should not pass:

- Order type.
- Time in force.
- Share quantities.
- Cash buffer.
- Limit price.
- Stop price.
- Side.
- Sequence number.

Those are planner responsibilities.

### 8.1 Target Portfolio Rules

The planner should validate `target_portfolio` before calculating orders.

Rules:

- Each item must include `symbol` and `target_weight`.
- `basket_id` is recommended for traceability.
- `target_weight` must be numeric and non-negative.
- Duplicate symbols should be combined by summing weights.
- Total target weight must not exceed 1.0 except for a small numeric
  tolerance.
- If total target weight is less than 1.0, the residual is treated as target
  cash.
- Symbols with zero target weight may be omitted from `target_portfolio`.
- Any current non-cash holding omitted from `target_portfolio` is treated as
  target weight zero.

## 9. Tool Output

The tool output should include the strict `execution_plan` plus diagnostics
for developer visibility.

Recommended output:

```json
{
  "schema_version": "1.0",
  "target_portfolio": [
    {
      "basket_id": "equity",
      "symbol": "SPY",
      "target_weight": 0.25
    }
  ],
  "current_vs_target": [
    {
      "symbol": "SPY",
      "basket_id": "equity",
      "current_quantity": 90,
      "current_price": 556.50,
      "current_value": 50085.00,
      "current_weight": 0.50,
      "target_weight": 0.25,
      "target_value": 25000.00,
      "delta_value": -25085.00,
      "planned_side": "sell",
      "planned_quantity": 45,
      "reason_code": "reduce_overweight"
    }
  ],
  "cash_projection": {
    "cash_before": 1000.00,
    "estimated_sell_proceeds": 25085.00,
    "estimated_buy_cost": 24800.00,
    "cash_after_estimate": 1285.00,
    "negative_cash_allowed": false
  },
  "execution_plan": {
    "schema_version": "1.0",
    "intent": "rebalance",
    "orders": [
      {
        "sequence": 1,
        "action": "submit_order",
        "symbol": "SPY",
        "side": "sell",
        "quantity_mode": "shares",
        "quantity": 45,
        "asset_type": "stock",
        "order_type": "market",
        "time_in_force": "day"
      }
    ]
  },
  "warnings": []
}
```

Only `execution_plan` is required by `execution_agent`.

The additional fields are for traceability and Agent Replay UI inspection.
They should not require the LLM to manually edit the final output.

## 10. Execution Plan Schema

The tool-generated `execution_plan` must match the existing strict execution
schema.

Required top-level fields:

```json
{
  "schema_version": "1.0",
  "intent": "hold",
  "orders": []
}
```

Allowed `intent` values:

```text
hold
rebalance
```

Each order must include:

```json
{
  "sequence": 1,
  "action": "submit_order",
  "symbol": "SPY",
  "side": "sell",
  "quantity_mode": "shares",
  "quantity": 45,
  "asset_type": "stock",
  "order_type": "market",
  "time_in_force": "day"
}
```

Rules:

- `quantity` must be a positive whole number.
- `side` must be `buy` or `sell`.
- `action` must be `submit_order`.
- `quantity_mode` must be `shares`.
- `order_type` must be `market`.
- `time_in_force` must be `day`.
- Limit, stop, stop-limit, trailing-stop fields are forbidden.
- Sell orders must appear before buy orders.
- Sequence numbers must be strictly increasing.

## 11. Calculation Behavior

### 11.1 Current State

The planner should collect current state from the strategy/runtime, not from
the LLM.

It needs:

- Current positions.
- Current cash.
- Current portfolio value.
- Last prices for every relevant non-cash symbol.

Relevant symbols are:

```text
union(current non-cash holdings, target portfolio symbols)
```

If a required price is unavailable, the planner should return a blocking
warning or raise a validation error rather than guessing.

### 11.2 Current Vs Target

For every relevant symbol:

```text
current_value = current_quantity * current_price
current_weight = current_value / portfolio_value
target_value = target_weight * portfolio_value
delta_value = target_value - current_value
```

Cash is not converted into an order. Residual target cash is handled by buying
less than 100% of portfolio value.

### 11.3 Sell Planning

Sell orders should be generated before buy orders.

Cases:

1. Current quantity is positive and target weight is zero:

   ```text
   sell all shares
   diagnostic reason_code = exit_removed_symbol
   ```

2. Current weight is above target weight:

   ```text
   reduce_value = current_value - target_value
   sell_quantity = floor(reduce_value / current_price)
   diagnostic reason_code = reduce_overweight
   ```

3. If calculated sell quantity is zero, omit the order and record a warning or
   diagnostic note.

The planner must never generate a sell quantity greater than current quantity.

### 11.4 Buy Planning

After estimating sell proceeds, buy orders should be generated for symbols
whose target value is above projected current value.

Cases:

1. Current quantity is zero and target weight is positive:

   ```text
   buy newly selected symbol
   diagnostic reason_code = buy_new_target
   ```

2. Current weight is below target weight:

   ```text
   buy additional shares
   diagnostic reason_code = increase_underweight
   ```

Buy sizing should use available projected cash:

```text
projected_cash = current_cash + estimated_sell_proceeds - estimated_prior_buy_cost
buy_quantity = floor(min(desired_buy_value, projected_cash) / current_price)
```

If projected cash is insufficient for at least one share, omit the buy order
and record a warning.

The planner must not generate a buy plan that projects negative cash.

### 11.5 Ordering

Order sequence should be deterministic.

Recommended ordering:

1. Full exits.
2. Partial reductions.
3. New buys.
4. Additions to underweight existing holdings.

Within each group, sort by symbol for stable test output unless a later design
adds a stronger ordering rule.

## 12. Relationship To Existing Drift Logic

Lumibot already has reusable drift calculation ideas in:

```text
lumibot/components/drift_rebalancer_logic.py
```

Relevant existing concepts:

- Current weight.
- Target weight.
- Target value.
- Drift.
- Sell when target weight is zero.
- Buy when current quantity is zero and target weight is positive.
- Reduce overweight assets.
- Increase underweight assets.

This feature should borrow or adapt those deterministic concepts where
practical, but it should not directly use `DriftOrderLogic` to place orders.

This planner is plan-only. It must not submit orders.

## 13. Prompt Changes

### 13.1 Portfolio Decision Agent

The `portfolio_decision_agent` prompt should be rewritten around a narrower
role.

It should say:

- Do not redo macro research.
- Do not redo basket research.
- Merge the macro allocation report and basket reports into a
  `target_portfolio`.
- Call `target_portfolio_to_execution_plan` with that target portfolio.
- Return only one valid JSON object with `decision`, `target_portfolio`, and
  `execution_plan`.
- The final `execution_plan` must be copied from the tool result.

It should explicitly forbid:

- Manual share calculations.
- Manual cash calculations.
- Manual order sequencing.
- Manually creating `execution_plan.orders`.
- Modifying tool-generated order quantities.
- Modifying tool-generated order side, order type, or time in force.

Suggested wording:

```text
Your job is to create the target portfolio from the macro and basket reports,
then call target_portfolio_to_execution_plan. Do not manually calculate share
quantities, cash usage, order side, or order sequencing. The planner tool owns
all execution_plan calculations. Your final JSON must include the planner
tool's execution_plan exactly as returned.
```

### 13.2 Portfolio Decision Agent Tools

The portfolio decision agent should not need direct account or market-price
tools for manual sizing.

Recommended tool set:

```text
target_portfolio_to_execution_plan
```

The planner tool can internally read account state and prices through the
strategy/runtime.

If direct account tools remain available for traceability, the prompt must
still forbid manual order sizing. The preferred first-version design is to
remove direct account and market-price tools from this agent to reduce
temptation and token usage.

### 13.3 Execution Agent

The execution agent prompt can remain narrow:

```text
Execute only the provided execution_plan. Follow sequence order. Submit each
order with the order tools. Confirm each submitted order. Stop on blockers and
report outcomes. Do not modify the execution_plan.
```

The execution agent should receive:

```json
{
  "date": "2024-09-06",
  "execution_plan": {}
}
```

It should not receive macro reports, basket reports, or target portfolio
reasoning unless a later debugging feature explicitly needs that.

## 14. Validation

The strategy must validate that the final summary did not replace the
tool-generated execution plan with an LLM-generated plan.

Recommended validation:

1. The planner tool stores the most recent planner result for the current
   strategy run.
2. After parsing `portfolio_decision_agent.summary`, the strategy compares:

   ```text
   parsed_summary.execution_plan == stored_planner_result.execution_plan
   ```

3. If they differ, block execution and record an error.
4. If no planner result exists, block execution and record an error.

This preserves scheme A while guarding against accidental LLM rewrites.

Existing validators should still run after this check:

- Execution plan schema validation.
- Buy-symbol validation.
- Sell quantity validation.
- Negative-cash prevention.

Some existing validators may become simpler because the planner now owns order
sizing.

## 15. Trace And UI Behavior

Because this design uses scheme A, the planner call should appear as a normal
agent tool call in the Agent Replay UI.

The UI should be able to show:

- Tool name: `target_portfolio_to_execution_plan`.
- Tool input: `date` and `target_portfolio`.
- Tool output:
  - `current_vs_target`.
  - `cash_projection`.
  - `execution_plan`.
  - `warnings`.

No new UI feature is required for the first implementation, but the tool output
should be human-readable enough for the existing tool-call panel to be useful.

## 16. Test Scenarios

### 16.1 All Cash To Target Portfolio

Input:

```text
Current: USD cash only
Target: SPY 50%, GLD 25%, VGIT 25%
```

Expected:

```text
Buy SPY
Buy GLD
Buy VGIT
No sell orders
No negative cash
```

### 16.2 Full Exit Plus New Buy

Input:

```text
Current: SPY 50%, GLD 25%, VGIT 25%
Target: SPY 50%, GLD 25%, TIP 25%
```

Expected:

```text
Sell all VGIT
Buy TIP
```

### 16.3 Full Rebalance Across Existing And New Symbols

Input:

```text
Current: SPY 50%, GLD 25%, VGIT 25%
Target: SPY 25%, GLD 50%, TIP 25%
```

Expected:

```text
Sell all VGIT
Sell part of SPY
Buy TIP
Buy more GLD
```

This is the critical regression test for the recently observed failure.

### 16.4 Basket Internal Symbol Switch

Input:

```text
Current: SPY 50%, GLD 25%, VGIT 25%
Target: QQQ 50%, GLD 25%, VGIT 25%
```

Expected:

```text
Sell all SPY
Buy QQQ
```

This proves the planner handles basket-internal selection changes, not only
macro basket-weight changes.

### 16.5 Drift Without Regime Change

Input:

```text
Target remains: SPY 50%, GLD 25%, VGIT 25%
Current after price movement: SPY 57%, GLD 28%, VGIT 14%
```

Expected:

```text
Reduce SPY if whole-share sizing allows
Reduce GLD if whole-share sizing allows
Buy VGIT if projected cash allows
```

This proves the planner handles ordinary price drift.

### 16.6 Hold Because Rounding Produces No Orders

Input:

```text
Current weights are close to target.
Delta values are too small to buy or sell one whole share.
```

Expected:

```text
intent = hold
orders = []
diagnostic warning explains whole-share rounding
```

## 17. Acceptance Criteria

The feature is complete when:

- `portfolio_decision_agent` calls `target_portfolio_to_execution_plan`.
- `portfolio_decision_agent` no longer manually calculates order quantities.
- Final portfolio-decision JSON still contains `decision`, `target_portfolio`,
  and `execution_plan`.
- The final `execution_plan` matches the planner tool output.
- The planner handles full exits, partial reductions, additions, new buys, and
  basket-internal symbol switches.
- The planner never emits limit/stop/trailing fields.
- The planner never emits negative projected cash.
- Unit tests cover the scenarios in section 16.
- A short backtest shows the planner tool call in Agent Replay UI.

## 18. Open Implementation Notes

Implementation should decide the exact file location for the deterministic
planner.

Preferred options:

1. Strategy-local helper module for the first experimental slice.
2. A reusable component under `lumibot/components` if the logic is cleanly
   general enough.

Recommendation:

Start strategy-local or component-local with tests. Promote to a broader
Lumibot component only after the API proves stable.

The implementation should also decide whether the planner uses existing drift
logic directly or copies the necessary calculation concepts. Direct reuse is
good if it does not force order submission or introduce strategy assumptions
that do not fit this workflow.

## 19. Risks

### 19.1 LLM Rewrites Tool Output

Risk:

The LLM may alter the planner-generated `execution_plan` in the final summary.

Mitigation:

Store the most recent planner result and compare the parsed final
`execution_plan` to the stored planner output before executing.

### 19.2 Market Prices Move Between Planning And Execution

Risk:

The planner uses one price snapshot, while market orders may fill at different
prices.

Mitigation:

First version only prevents projected negative cash based on current prices.
Real-time fill slippage is not solved in this slice. Whole-share rounding will
usually leave residual cash. More advanced cash buffers or broker fill-aware
logic can be added later.

### 19.3 Tool Becomes A Hidden Optimizer

Risk:

The planner could gradually accumulate strategy logic that belongs elsewhere.

Mitigation:

Keep the planner deterministic and narrow: current portfolio plus target
portfolio in, execution plan out. It should not decide target weights or target
symbols.

### 19.4 Existing Drift Logic Does Not Fit Exactly

Risk:

Existing drift rebalancer code may place orders directly or assume a different
workflow.

Mitigation:

Reuse calculation concepts first. Do not couple the new planner to direct order
submission.

## 20. Future Extensions

Potential later work:

- Configurable drift thresholds.
- Configurable cash target or cash buffer.
- Fractional shares.
- Broker-aware buying power checks.
- Fill-aware second-pass planning after sell confirmations.
- UI view dedicated to current-vs-target transition plans.
- Real macro regime classifier replacing the mock classifier.
- Linearized regime weights instead of four fixed 50/25/25/0 points.

These are intentionally excluded from the first version.
